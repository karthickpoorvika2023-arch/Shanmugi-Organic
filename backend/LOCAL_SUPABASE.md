# LOCAL Docker Supabase (no hosted project changes)

Run from the repository root. Docker Desktop must already be running.

1. `cd backend && npx supabase start` — local project ID is `backend`; never `supabase link`, `db push`, or deploy to a hosted project. Run `npx supabase migration up --local` if the local stack was created before these migrations.
2. `npm run local:seed` regenerates `backend/supabase/seed.sql` from the bundled payment catalog. The seed is applied automatically on a **new** database or `supabase db reset --local` (the latter **deletes local data**). On an existing local DB, import the seed using the local Studio SQL editor only. Each product has one primary size; the other storefront sizes cannot be submitted to demo checkout yet.
3. Set `LOCAL_ADMIN_EMAIL` and a unique `LOCAL_ADMIN_PASSWORD` (12+ characters) in your terminal, then `npm run local:admin`. This creates a *new* user in LOCAL Auth and adds their UUID to the LOCAL allowlist. Do not reuse production login credentials. Do not put passwords in files, URLs, command-line arguments or screenshots.
4. `npm run dev:local` starts the preview at `http://localhost:4173/` and the local `demo-payment-kit` Edge Function. For an already running local function server, `npm run dev` runs just the preview. Open `http://localhost:4173/admin.html` and log in with the local account. Local Studio: `http://127.0.0.1:54323`; local Mailpit: `http://127.0.0.1:54324`.
   **Admin login troubleshooting:** Do not open `frontend/admin.html` through VS Code Live Server, `file://`, or a server serving `dist/` for LOCAL login: those servers do not inject the LOCAL Supabase configuration. If you see "Local Supabase configuration unavailable", use the preview URL above instead. If you see "Login SDK unavailable" on a published site, verify that `plugins/supabase/supabase.umd.js` and `plugins/supabase/supabase-client.js` were uploaded alongside `admin.html` from the same `dist/` build. A store/signup user is not automatically an admin; create a separate LOCAL admin with step 3 and use that account. Never use production credentials in LOCAL development.
5. `npm test`, `npm run build`, `npm run test:local`, `node tools/signup-browser.test.mjs`, `node tools/admin-login-browser.test.mjs` verify functionality. The integration smoke test makes disposable local users and cleans them up.

**Signup email during local development:** Docker Supabase sends confirmation codes to the **local Mailpit inbox** at `http://127.0.0.1:54324`, not to Gmail or your real email provider. Search Mailpit for the signup address and use the latest six-digit code on `verify-otp.html`. If it has expired, wait for the page's Resend button, request a new code, and check Mailpit again. The local Auth config has no external SMTP credentials; do not enter production SMTP secrets or assume a message arrived in a real inbox.

**Forgot password in local preview:** Open `http://localhost:4173/forgot-password.html`, enter an account email and select **Send Reset Code**. The page opens recovery OTP verification (not the Check Your Email screen). Look for the six-digit code in the styled recovery email in `http://127.0.0.1:54324` (Mailpit), **not in your Gmail inbox**. Enter the code to open the standalone reset-password form; change the password there to enter the home page. A wrong code does not open the reset form or home page. If you open `frontend/forgot-password.html` through VS Code Live Server (usually port 5500), it redirects to the running local preview: Live Server cannot inject the local Auth configuration. A failed/stalled request restores the button after at most 15 seconds. Restart the local Supabase stack to load email template changes. This configuration is **local only**: hosted Supabase recovery still uses its existing reset link unless you configure the recovery email template and equivalent hosted flow separately. This browser flow is not enforced MFA for direct Auth API requests. Use a local test account, not real credentials.

**Signup OTP flow:** Sign up on `http://localhost:4173/signup.html` to open `verify-otp.html` with your signup email. A correct six-digit signup code establishes a session and returns you to the store home page; an incorrect or expired code leaves you on the verification page with an error. Opening the verification page directly without a signup email cannot verify a code. Existing users use the normal email and password fields on `signin.html`; there is no separate **Email me a sign-in code** button.

**Local existing-user sign-in OTP:** On the local preview, sign out, then enter your existing confirmed account email and password on `http://localhost:4173/signin.html` and click **Sign In**. The loopback-only preview server checks the password without giving that session to the browser, sends a six-digit code via Supabase to Mailpit (`http://127.0.0.1:54324`), and opens `verify-otp.html?mode=signin`. A correct code starts a browser session and opens the home page; a wrong code leaves you on OTP verification without a browser session. To request another sign-in code, return to Sign In, wait at least 60 seconds, and re-enter your password. The separate Magic Link email template in `supabase/templates/signin-otp.html` renders a **numeric code**, not a clickable link. Restart the local Supabase stack to load the new template and restart the preview server to load the new endpoint. Neither this template nor this local-only UI flow is deployed to the hosted project; local emails appear in Mailpit, not your real inbox. **Not enforced MFA:** direct Supabase Auth password requests can still produce sessions outside this UI; do not rely on this flow to protect sensitive resources from clients calling Auth directly. Enforced MFA requires server-side access enforcement or Supabase Auth MFA configuration.

**One-time cloud → LOCAL merge:** `tools/merge-cloud-to-local.mjs` reads an *existing private* cloud CLI `data.sql` export and requires separate, complete cloud and local backup directories. Set `CLOUD_BACKUP_DIR`, `LOCAL_BACKUP_DIR`, and (if Docker is not on PATH) `LOCAL_DOCKER_CLI` in the terminal. Run `node tools/merge-cloud-to-local.mjs --dry-run` first; it stages data, checks conflicts, and always rolls back. To apply after checking the plan, set `CONFIRM_LOCAL_MERGE=LOCAL_ONLY` and run `node tools/merge-cloud-to-local.mjs --apply`. It writes **only** to the `supabase_db_backend` Docker container, in one transaction. It does not link this workspace to the cloud project. Existing local user/password/profile and catalog UUIDs are retained; a matching cloud email is mapped to the local user ID; shared catalog slugs receive cloud details. It imports new Auth users and email identities, categories, products, orders, order items and banners with a read-only active-banners policy. It **does not** import cloud sessions, refresh tokens, MFA state, storage files or cloud admin allowlist/privileges. Existing users may need to sign in again; explicitly approve a local admin separately. Other cloud tables/features are outside this scoped merge. This is a snapshot, **not continuous synchronization**: future changes do not flow automatically in either direction. Never commit or share the SQL exports (they contain personal information and password hashes).

**Imported-user login repair:** Older one-time imports may leave GoTrue string token fields in `auth.users` as `NULL`, making local password sign-in fail with **"Database error querying schema"**. First take a fresh *post-merge* LOCAL roles/schema/data backup into a private folder (the original pre-merge backup does not contain imported users). Set `LOCAL_PRE_AUTH_FIX_BACKUP` to that folder and `LOCAL_DOCKER_CLI` if needed. Run `node tools/repair-local-auth-tokens.mjs --dry-run` to confirm affected row counts; then set `CONFIRM_LOCAL_AUTH_REPAIR=LOCAL_ONLY` and run `node tools/repair-local-auth-tokens.mjs --apply`. This changes only four NULL token columns in the LOCAL Docker database; it does not alter passwords, cloud data, admin privileges or user IDs. Set `LOCAL_PRE_MERGE_BACKUP` to the original pre-merge LOCAL backup folder and run `node tools/local-auth-login.test.mjs` to check that a deliberately wrong password for an imported user returns HTTP 400 rather than an Auth schema error. The merge tool now writes empty strings in these token fields for newly imported users. Admin access still requires a separate local approval/allowlist entry; do not reuse the password exposed in a screenshot.

The preview server injects only LOCAL API URL and the local **anon/public** key from CLI status. No service-role key is exposed to the browser. If local config cannot load, localhost fails closed rather than switching to a hosted project. Opening `frontend/` or `dist/` with another localhost web server is deliberately **not configured**: use `npm run dev:local` (or `npm run dev`) for local testing. Hosted static build remains independent of this runtime endpoint. Demo checkout records no real orders or payments; catalog sync from admin is disabled. Local CMS publishing requires explicit admin allowlisting.
