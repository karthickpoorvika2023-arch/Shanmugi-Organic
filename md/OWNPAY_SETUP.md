# OwnPay checkout: deployment checklist

This integration **does not collect payments until configured**. The storefront is in INR; the deployed OwnPay brand must have an enabled **INR-capable** gateway and registered INR currency. OwnPay is a separate self-hosted PHP/MySQL application (not included here). Set up a merchant account and test that gateway separately. Do not use the OwnPay public demo for real payments.

## If checkout says “Failed to fetch”

The browser cannot read the Edge Function response, often because the function does not exist in the Supabase project or the OPTIONS preflight is blocked by the deployment/origin configuration. Check that `ownpay-checkout` is **ACTIVE** under Supabase → Edge Functions for project `ufhlmdqkqdkcohpbzdux`. A request to `/functions/v1/ownpay-checkout/create` returning **404** means the checkout function is missing; editing only the storefront cannot deploy it. After deploying, set `STORE_ORIGIN` to the exact public **HTTPS origin** serving the checkout (including any `www` prefix). Configure the remaining secrets below. In browser DevTools → Network, examine the `OPTIONS` and `POST` requests to `/functions/v1/ownpay-checkout/create`: `404` means missing function; a CORS error means origin/preflight mismatch; a JSON `503` means the payment service is not configured or unavailable. Never put gateway secrets in browser code. Do **not** bypass verification by showing a paid order on a network error.

1. Install OwnPay on a private HTTPS domain, connect an INR-capable merchant provider in OwnPay and enable INR. Configure the OwnPay brand, API key and webhook secret in its dashboard. Verify the provider's settlement and callback settings with that provider.
2. Set the Supabase Edge Function secrets **in Supabase only**, never in `frontend/`, `.env.example`, chat, or Git: `OWNPAY_BASE_URL` (your OwnPay brand HTTPS origin), `OWNPAY_API_KEY` (merchant API key), `OWNPAY_WEBHOOK_SECRET`, `STORE_ORIGIN` (exact HTTPS storefront origin). `SUPABASE_SERVICE_ROLE_KEY` and `SUPABASE_URL` must exist in Supabase Edge Functions' environment; never publish either service-role key.
3. Review and run `backend/schemas/ownpay-checkout.sql` in the existing Supabase project SQL Editor. **Impact:** unauthenticated read of all customers' orders and public order writes/status edits (including the current browser-only admin orders list/status dropdown) are disabled, because they expose customer addresses and allow paid-order forgery. Set up a separately authenticated admin server endpoint before relying on browser admin order management. Do not rerun the old `supabase-schema.sql` or `FIX_ADMIN_ORDERS.sql` after this migration: those scripts recreate unsafe public policies. Old unverified/demo orders remain in the database; audit them and do not treat them as paid invoices.
4. Run `node tools/gen-payment-catalog.mjs` whenever catalog base prices change. Deploy `backend/supabase/functions/ownpay-checkout/` as Supabase Edge Function `ownpay-checkout` with `verify_jwt = false` **only because** the handler itself checks user JWT for create/status and verifies HMAC on the public webhook. Example CLI: change directory to `backend/` (it contains `supabase/functions/`), then run `supabase functions deploy ownpay-checkout --project-ref ufhlmdqkqdkcohpbzdux --no-verify-jwt`. Do not deploy until database migration and secrets are in place.
   The merchant API field for a customer's email is `customer_email`; check the installed OwnPay release's API response and registered INR gateway in sandbox before taking live payments.
5. Deploy the static site (`npm run build`); set `STORE_ORIGIN` to its exact public HTTPS origin. Test a **gateway sandbox transaction** for success, failure, cancellation, duplicate webhook, replay signature, mismatched amount and return without webhook. A return URL alone never creates an order. No invoice generation or refund endpoint is provided by this patch.

## Admin dashboard → Payment Gateway

After reviewing and applying `backend/schemas/ownpay-checkout.sql`, add each **trusted admin's Supabase Auth user UUID** to the server-owned allowlist in the Supabase SQL Editor (replace the sample UUID below with the actual UID; do not use a customer's UID):

```sql
INSERT INTO public.ownpay_payment_admins (user_id)
VALUES ('00000000-0000-0000-0000-000000000000')
ON CONFLICT (user_id) DO NOTHING;
```

Find the real UUID in Supabase → Authentication → Users. The existing `admin.html` login verifies only that a Supabase user is signed in; **it does not prove admin privileges**. The Payment Gateway page additionally verifies the JWT against Supabase Auth and checks this server-side allowlist before any payment data is returned. Do not put service-role or merchant keys in the browser, do not grant `anon`/`authenticated` direct reads of `ownpay_checkouts`, and do not create public read policies for payments. This page is a read-only report of the latest 50 attempts per page: customer contact, amount, status, provider payment/transaction IDs, items and paid date. `pending` means **not verified/collected** (it can also mean a failed or cancelled attempt); only server-reconciled `paid` counts toward collected totals. The summary totals apply to the **visible page**, not the entire history. Previous unverified/demo orders are not included.

**Important:** The older Orders/Customers admin pages have legacy public data-access policies. Running the secure checkout migration intentionally disables public order reads/writes and will break the browser-only Orders management until a separate authenticated admin API is implemented. The payment report does not reinstate those unsafe permissions. Do not run this migration in production without planning the admin Orders replacement.

The server recalculates fixed prices using the generated catalog snapshot; admin-created local/browser-only products and prices are intentionally rejected until they are synchronized to a trusted server-side catalog. A previously started checkout can be checked again from the checkout page before paying twice. Browser cart/local tracking copy is not authoritative; only a paid order recorded by the backend is authoritative.
